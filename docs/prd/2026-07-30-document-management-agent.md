# PRD：文档管理 Agent（第一阶段）

> 状态：当前开发基线  
> 日期：2026-07-30  
> 历史平台方案：[多智能体项目数据平台（历史 PRD）](2026-07-30-historical-multi-agent-data-platform.md)

## 1. 产品定义

文档管理 Agent 是一个单一 Agent，不是三个独立 Agent。它组合三个 Skill：

- `document_parse`：按文件能力原生解析或 OCR，生成标准化文档事实；
- `business_query`：保留业务查询和待审核建议入口；第一阶段不负责项目归属判断；
- `archive`：仅保留显式确认后的安全执行能力；第一阶段不运行真实归档。

第一阶段目标是把用户明确指定的业务文件，转换为**可审核、可追溯、可查询**的解析交付物。它必须让用户直接回答：

```text
Agent 处理了什么文件？
实际使用了什么解析能力？
读到了什么内容？
提取了哪些字段、证据是什么？
源文件是否被修改？
本次运行产生了哪些结果？
```

## 2. 第一阶段范围

### 2.1 输入与安全边界

- 仅处理用户在单次任务中明确指定的文件。
- 源文件绑定必须是只读；`prepare` 不得移动、改名、复制、删除或覆盖源文件。
- 真实归档必须经独立确认调用 `execute-confirmed`；第一阶段验收不执行该动作。
- 原始业务文件、运行数据库和结果产物均在 Git 仓库外保存。

### 2.2 支持的解析路径

- 文本与结构化文件：TXT、Markdown、CSV、JSON、XML。
- Office：DOCX、XLSX、XLSM。
- PDF：先尝试原生文本提取；没有可用文本时使用已声明、实际可用的 OCR Provider。
- 图片与扫描件：使用已安装的 OCR Provider；当前已在真实文件验证 EasyOCR。
- Provider 顺序声明为 RapidOCR、MinerU、EasyOCR；未安装或模型不可用必须返回明确、可审计的状态，不得运行时下载模型。

### 2.3 正式交付产物

每份文件必须在外部结果目录生成：

```text
<results-root>/runs/<run-id>/documents/<document-id>/
  document.json
  review.md
```

每次运行必须在同一运行目录生成：

```text
run.json
run-summary.md
```

`document.json` 是该次处理的机器可读事实快照；`review.md` 仅从 `document.json` 渲染，不维护第二份事实。历史运行不得被重跑结果静默覆盖。

### 2.4 结构化事实

每份 `document.json` 至少包含：

- 文档身份：逻辑 URI、原始文件名、内容哈希、MIME 类型；
- 运行身份：`run_id`、Agent/Skill 版本、运行时间、只读与未归档声明；
- 解析事实：状态、实际解析器、Provider 尝试记录、原文、页码块、表格、警告和失败原因；
- 提取事实：文件类型及按类型扩展的字段；每个候选值可附置信度与来源证据；
- 处理建议：第一阶段固定为不归档或待审核，不做项目归属结论。

字段结构固定为“字段名、候选值、置信度、证据”，业务字段名单按文件类型扩展，不能以单一项目名称规则覆盖所有文件。

第一批必须支持的发票事实包括：

```text
发票类型、发票号码、开票日期、购买方、销售方、双方税号、
不含税金额、税额、价税合计、税率、服务或商品内容、备注。
```

### 2.5 SQLite 索引与审计

第一阶段继续使用节点本地 SQLite。数据库保存跨运行查询所需的索引，不替代完整 `document.json`：

- `documents`：哈希、媒体类型、解析状态、解析器、关键字段索引；
- `document_locations`：原始文件逻辑 URI 和位置历史；
- `organization_runs`：任务目标、时间、状态；
- `organization_items`：任务中的文件、建议和处理状态；
- 结果产物的逻辑 URI、产物哈希或等价可验证引用。

## 3. 运行模型

```text
明确输入文件
  -> 文档管理 Agent / prepare
  -> 原生解析或 OCR
  -> structured_document
  -> document.json（唯一事实来源）
  -> review.md（人工审核视图）
  -> SQLite 索引与运行审计
  -> run.json + run-summary.md
```

若解析失败，仍必须生成可审核结果，说明失败阶段、失败原因、已尝试 Provider 和建议人工动作；不得把失败伪装为成功。

## 4. 明确非目标

以下内容不属于第一阶段完成条件：

- 旧版 `.doc` 解析；
- 数据库 + PageIndex 的项目归属判断效果；
- 项目、主体、合同、别名等业务记忆模型；
- PostgreSQL、群晖、异地执行节点部署；
- 真实文件的自动或人工确认归档执行；
- 浏览器自动化、CRM/BPM 写入；
- 自动修改 Skill、自动写入长期业务记忆；
- 全盘扫描 SynologyDrive 或批量 OCR。

## 5. 开发计划

### 里程碑 1：产物契约与结果根目录

- 定义 `document_result.v1`、`agent_run.v1` 和可读审核视图的最小契约。
- 节点本地配置显式声明结果根目录；结果根目录不可位于 Git 仓库或源业务目录。
- 为运行目录、文档目录、逻辑 URI 和重跑版本建立确定性命名规则。

**验收：** 单文件 `prepare` 后能定位一个独立运行目录，且源文件不变。

### 里程碑 2：正式 JSON / Markdown 交付

- 由解析结果正式写出 `document.json`。
- 从同一 JSON 渲染 `review.md`、`run.json`、`run-summary.md`。
- SQLite 保存产物的可验证引用，不只保存部分字段。

**验收：** 用户不打开 SQLite 或终端，也能通过 `run-summary.md` 找到并审核每份结果。

### 里程碑 3：类型化字段提取

- 引入文件类型识别与通用候选字段表达。
- 首先实现电子发票字段抽取；保留证据、置信度和未识别字段。
- 保证“未识别”与“识别为空”可区分，避免编造项目名称或业务事实。

**验收：** 对真实电子发票能在 `document.json` 和 `review.md` 展示购销双方、日期、金额和服务内容；项目归属仍明确为不在当前范围。

### 里程碑 4：审计一致性与错误语义

- 修正格式不支持、Provider 不可用、模型不可用、OCR 为空、原生解析失败等错误码。
- 确保解析状态、SQLite 索引、`document.json` 与 `review.md` 一致。
- 记录实际 Provider 尝试，但不泄露物理路径、凭据或模型配置敏感信息。

**验收：** 旧 `.doc` 返回明确的“不支持”结果；扫描 PDF、文本 PDF 与失败文件均生成完整审核产物。

### 里程碑 5：小样本真实验收

- 使用明确指定的少量真实文件，不扫描业务根目录。
- 至少覆盖一份扫描 PDF 与一份电子发票 PDF。
- 核验解析内容、页码/文本、字段、产物位置、SQLite 记录和源文件不变。

**验收：** 人工可通过结果目录评估 Agent 的解析质量；所有文件维持 `prepare` 状态，无真实归档动作。

## 6. 完成定义

满足以下条件时，文档管理 Agent 第一阶段完成：

1. 对明确指定的支持格式文件，能原生解析或通过可用 OCR 生成完整、可审核的结果；
2. 每份文件有正式 `document.json` 和 `review.md`，每次运行有 `run.json` 和 `run-summary.md`；
3. 扫描 PDF 和电子发票 PDF 已经通过真实文件验收；
4. 发票关键事实可被提取、展示并标注证据；
5. SQLite 可以追溯文件、位置、运行、处理项和结果产物；
6. 失败结果透明、错误语义准确；
7. 源文件始终未修改，未触发真实归档；
8. 不依赖旧 `.doc`、PageIndex 判断效果、PostgreSQL 或群晖部署。

## 7. 后续迭代入口

第一阶段完成后，按历史 PRD 的顺序迭代：

1. 人工审核结果与项目/主体主数据；
2. 数据库候选 + PageIndex 证据的项目判断对照；
3. 显式确认的归档执行；
4. PostgreSQL / 群晖部署；
5. 更细粒度的 Agent 权限与协作。
