# 历史 PRD：多智能体项目数据平台

> 状态：历史架构基线，保留供后续迭代；不作为当前开发范围。  
> 日期：2026-07-30  
> 关联设计：[多智能体数据平台设计](../superpowers/specs/2026-07-23-multi-agent-data-platform-design.md)

## 1. 背景

项目早期希望同时覆盖文件解析、项目管理、业务记忆、归档、浏览器自动化、跨设备执行和中心化数据库。由此形成了“主助手 + 多个职责 Agent + SQL + PageIndex + 存储适配器”的平台方案。

该方案解决的是长期目标，不是当前最小可用产品。它包含的能力边界较多，若在第一个可用 Agent 尚未形成可审核交付物前同时推进，容易造成架构、代码和真实业务验证脱节。

## 2. 历史目标

- 主助手接收办公与项目管理任务，并将任务交给具备明确权限边界的专业 Agent。
- 文档分析 Agent 负责只读解析、候选事实、证据和归档意图。
- 项目账本 Agent 审核候选事实并写入权威项目数据。
- 归档执行 Agent 只执行经人工确认的文件移动、改名和回读校验。
- 浏览器自动化 Agent 在后续阶段处理外部系统读取、草稿和受审批提交。
- SQLite 支持单机运行；PostgreSQL 支持群晖中心化运行；Windows/macOS 节点通过能力与逻辑存储绑定执行任务。
- SQL 保存权威业务事实，PageIndex 提供长文档章节、页码和局部上下文证据；JSON/Markdown 是可重建的审核视图与审计快照。

## 3. 历史逻辑架构

```text
用户 / Claude Code / 触发器
  -> 办公与项目管理主助手
       -> 文件与文档分析 Agent（只读）
       -> 项目账本 Agent（权威事实写入）
       -> 归档执行 Agent（经确认的文件写入）
       -> 浏览器自动化 Agent（后续）

数据与能力层
  -> SQL：项目、主体、关系、审核、运行与任务
  -> PageIndex：长文档章节、页码、局部证据
  -> DocumentStore：原始文件与大型产物
  -> OCR / 原生解析：标准化文档事实
  -> JSON / Markdown：可读审核视图
```

## 4. 应保留的设计原则

即使当前收敛到一个文档管理 Agent，以下原则仍然有效，后续迭代不得丢失：

1. **物理路径不是文档身份。** 使用逻辑 URI、内容哈希和 StorageBinding 区分业务身份与节点本地路径。
2. **原始业务文件不进入 Git。** 仓库只存代码、契约、迁移、匿名夹具和示例配置。
3. **派生产物可审核。** JSON/Markdown 不是隐藏的内部状态，而应让人能复核 Agent 的事实、证据和建议。
4. **模型推测不能直接成为权威事实。** 候选事实须有来源、状态和人工确认边界。
5. **归档与外部写入必须显式确认。** 解析、判断和归档是不同权限级别的动作。
6. **PageIndex 是证据定位能力。** 它不替代数据库，也不应被当作权威业务事实库。
7. **能力按需启用。** OCR、PageIndex、LLM、数据库部署和浏览器自动化均由实际任务触发，不强制所有节点具备。

## 5. 暂缓原因

以下能力依赖真实运行产物、字段质量和人工审核反馈；在基础文档管理能力尚未完成前，不应作为当前实现前提：

- 多 Agent handoff 与权限编排；
- 项目主数据、别名、项目—主体关系和业务记忆沉淀；
- 数据库 + PageIndex 的项目归属判断效果；
- PostgreSQL、群晖中心化控制平面和异地执行节点；
- 浏览器自动化与外部系统写入；
- 已确认归档的真实业务文件执行。

## 6. 重新启用条件

当 [文档管理 Agent 开发计划](2026-07-30-document-management-agent.md) 的第一阶段验收完成后，才按业务价值逐项恢复本 PRD 中的能力。建议顺序：

1. 项目主数据与人工确认的业务事实；
2. PageIndex 长文档证据和数据库候选的对照验证；
3. 经确认的归档执行；
4. PostgreSQL / 群晖部署；
5. 多 Agent 权限拆分与浏览器自动化。

## 7. 非目标

- 不删除或否定历史设计、既有 Skill 或接口；
- 不把历史多 Agent 方案伪装成当前已实现能力；
- 不在当前阶段自动迁移到 PostgreSQL、连接群晖或运行浏览器自动化；
- 不让任何 Agent 未经确认移动真实业务文件。
